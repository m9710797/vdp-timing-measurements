Hi,

Yet another status update. Short summary: I figured out where in
time there are VRAM access slots located that can be used for CPU
or command engine read/writes. I did not yet figure out how these
free slots are allocated to either cpu or command engine.


In the previous status update I figured out how the refresh, bitmap
and sprite rendering accesses VRAM. When screen is disabled there
are only refresh accesses (not 100% true, see below). When you
enable screen (without sprites), those refresh accesses remain and
you add fetches for the bitmap data. Similarly, when you also enable
sprites, the previous accesses remain and you add the sprite
accesses.

My next goal was to extend this schema with either CPU or command
engine accesses. Unfortunately this was a bit too difficult for me
to do in a single step. It turns out that cpu and command accesses
cannot simple be 'added' to this schema. Depending in which of the
three access-modes (I mean screen-off, sprites-off or sprites-on)
the VDP is, the cpu/command accesses occur in totally different time
slots. So it's NOT the case that in mode 'sprites-on' there are N
slot available, going to mode 'sprites-off' adds some slots and mode
'screen-off' adds even more. Instead the position of the slots is
completely different in these three modes. It also seems to be the
case that all of these 'free slots' can be used for either cpu or
command accesses.

So instead of figuring out the whole CPU or command access stuff I
first looked at a simpler problem. Just locating the positions of
possible cpu OR command engine access slots. I did NOT yet look at
when the CPU or command engine actually gets a slot (one likely
possibility is that it simply gets the first available slot). I did
also NOT yet investigate what happens when both the CPU and the
command engine want an access slot at the same time (possibilities
are: one always gets priority, or the earliest requester gets
priority, or round-robin, or ...).


The next few paragraphs tell how I figured out the slot locations,
feel free to skip to the next non-indented paragraph if you're only
interested in the actual results.

  Ok, so where are the cpu/command access slots located? I already
  annotated the log files with the type of the access, so a simple
  grep '[RW]\.[ec]' can filter the cpu/command access. And with some
  more text processing you can get a list of the time slots. I did
  this separately for the three 'VDP-access-modes'.

  Initially I only did this for the screen-off mode and separately
  for cpu and command access. The list of command accesses was
  largest. There was a large overlap between the lists but either
  list contained elements that were not present in the other list.
  If you look at the type of tests that we captured, you see that we
  did more tests using commands (and our most tested commands HMMV
  does more accesses per time than what the CPU can do). So it's
  logical that the list of command accesses is more complete. But
  how can we be sure to get a 100% complete list?

  So I took a closer look at the union of the cpu and command access
  lists. I looked at the time interval between two successive
  accesses and I got a fairly regular pattern (remember I'm only
  looking at the screen-off mode). Mostly there are 8 cycles between
  the possible slot locations. But I got one gap of 44 and one of 40
  cycles. There were also 8 gaps of 16 cycles and 2 gaps of 10
  cycles.

  All gaps of 16 cycles were located 'over' a refresh-read. The gap
  of 40 cycles was located over 4 reads of address 0x1ffff (for some
  reason there are these 4 dummy reads when the screen is turned
  off, located at cycles 1237, 1245, 1253 and 1261, but not in the
  other two modes). So if we assume that cpu/command slots can only
  start every 8 cycles, these numbers make sense. The two gaps of 10
  cycles are located at cycle 1335 and 1345 (so next to each other).
  This is also the location where the sprite timing was a bit
  irregular (also 2 times 2 extra cycles), so this might be OK. The
  gap of 44 cycles goes from 121-165. If you look at the union of
  really _all_ access there never seems to start any access in the
  interval 129-163 (but that's only a gap of 34).

  So is there a slot missing from our list located around that gap
  of 44 cycles? Also the fact that slots seem to start every 8
  cycles (while an access only requires 6 cycles), might that just
  be a coincidence caused by our method of testing? E.g. we
  read/write bytes from/to the CPU every 72 VDP cycles (12 Z80
  cycles) and 72 is a multiple of 8.

  I got my answers when I looked back at the original VCD trace (for
  something not directly related). I noticed that the RAS signal was
  constantly toggling, even if there were no actual VRAM access
  going on (I noticed this before, but back then I didn't gave this
  further attention). These toggles seemed to correspond to the
  gap-pattern I got above. So I wrote a script to extract/translate
  these toggles to cycle numbers and I got the exact same list of
  number I got above. (So the union of cpu and command accesses _was_
  a complete list.)

  To further verify this result, I extracted the RAS-toggles from
  all the captures. I only got three distinct patterns and these
  correspond to the three different VDP access modes: screen-off,
  sprites-off, sprites-on. (So even when the VRAM bus could have
  been idle, the RAS signal is toggling and thus causing
  RAS-without-CAS refresh accesses, far from ideal from a
  power-usage point of view, but I guess that was not an issue in
  those days).

  Ok, so I got the slots for the screen-off mode, and I'm now fairly
  confident the numbers are correct. Now the two other modes. For
  sprites-on, the list of numbers I got via processing the accesses
  and via the RAS-toggles (and subtract the toggles for know
  accesses) matched 100%. Though for the case sprites-off this list
  obtained via RAS toggles was longer than the list obtained via
  filtering (but the RAS-toggle list was a strict superset).

  We do have a lot of captures (47) for the access-mode screen-off.
  We have less captures (14) for the mode sprites-on but this mode
  has the least number of 'free' access slots (so you need less
  capture data to have an equal chance of filling all slots). For
  the mode sprites-off we only have 8 captures. So maybe it's not
  surprising that the list of accesses slots we got by processing
  the seen accesses is incomplete for the sprite-off mode. I think
  it's fairly safe to assume that also for this mode, the RAS
  toggles can be used to locate all free access slots.

So now the results. At the end of this text I've pasted the numbers.
This is a table with 4 columns. The first column is the time in VDP
cycles (as usual this is the time of the falling CAS edge, and the
zero-point is still arbitrary). The next 3 columns are for the modes
screen-off, sprites-off, sprites-on. A non-empty cell in these
columns means that at this moment in time there can _possibly_
happen a cpu or command access (remember I did not yet figure out
how the VDP actually allocates these slots to cpu and command). The
number in these three columns is simply the distance from the
previous slot (so the 'gap' from the discussion above).

I didn't verify all the details of this table (for mode screen-off I
did, but for the other two modes only to a certain degree), but at
first sight all the irregularities in these gaps can be explained by
the other accesses that the VDP has to do (refresh, bitmap or sprite
fetches).


So next step is to figure out how these 'free slots' are actually
used by the CPU and command engine accesses. And as usual feel free
to help.
